# CaliPark audit 2026-11-03: all findings

Generated from a 7-dimension audit. Each dimension had one finder agent and one adversarial verifier that tried to refute every finding against the code. 136 findings were kept and 0 were refuted. `verdict: partially` means the verifier confirmed the issue but adjusted its severity or scope.

The summary and priorities are in [README.md](README.md). This file is the detailed reference with evidence and fixes. Line numbers refer to commit `c0e71eb`.


## A. Logic bugs: Skills / progression / rewards

The Skills domain is mostly sound. The catalog matches PROGRESSIONS.md 1:1 (64 unique exercise IDs, no duplicate UUIDs, measurement matches criterion), the rep-bucket mapping from 7451f8c matches the truth doc, and the level and XP formulas are correct. The real defects are in state that persists across calibration and in the reward loop. Recalibrating wipes every declaration the user did not re-enter. Lowering the placement floor makes long-conquered rungs celebrate again with a false "+100 XP". The engine ignores the parallel band track, so band-less beginners are told to train band pull-ups and the "Mam gumę" answer has no effect. Celebrations are marked as celebrated before they are ever shown. Lower-severity issues: sets are scored per log entry rather than per session, which breaks RR-style supersets; rung identity is stored as an array index; the mapping change shipped without migrating saved placements; and there are several UX and copy gaps.

### A-1 [high] Re-calibration silently erases every declaration the user does not re-answer

- **Where:** `cali-park/Features/Skills/ViewModels/PlacementCalibrationViewModel.swift:39`; also `cali-park/Features/Skills/Services/SkillPlacementStore.swift:16`, `cali-park/Features/Skills/Views/PathDetailView.swift:63`, `cali-park/Features/Skills/Views/SkillPathsView.swift:74`
- **Effort:** M · **Verdict:** confirmed
- **Evidence:** Init only preloads the band: `ownsBand = store.load()?.ownsEquipment(PlacementCalibration.bandEquipment) ?? false` (L39), while `private(set) var repAnswers: [ProgressionPathID: RepCountBucket] = [:]` (L20) and `masteredSkills: Set<String> = []` (L22) always start empty. `save()` (L79-81) does `try store.save(placement)`, and PlacementStoring.save is documented as "Persists the placement, replacing any previous declaration." (SkillPlacementStore.swift:16). PathDetailView exposes this as a per-path "Ustaw poziom" (PathDetailView.swift:41, 63-64), and so does the SkillPathsView toolbar (SkillPathsView.swift:55-61).
- **Impact:** An athlete who onboarded with pull-ups 1–5 (pullUp=4), push-ups 6–11 (pushUp=3) and the muscle-up checkbox (muscleUp=3) later opens "Ustaw poziom" from the Dips ladder, answers only the dips question and taps Zapisz. The saved placement is now `{dip: 2}`. The pull-up, push-up and muscle-up paths drop back to rung 0 (unless logs prove more). The form showed no previous answers, so nothing warned the user. The lowered floors also trigger the celebration flood described in A-2.
- **Fix:** Pre-fill the form from the saved placement: map each declared rung back to a bucket when unambiguous and pre-check skill boxes whose rung is declared. Alternatively, make save merge: only overwrite paths the user actually answered in this session and keep the other declarations. Add a VM test where a partial re-calibration keeps untouched paths.
- **Verifier:** Checked PlacementCalibrationViewModel.swift. L20 `repAnswers = [:]` and L22 `masteredSkills = []` always start empty, and only `ownsBand` is pre-filled from the store (L39). `save()` (L79-81) calls `store.save(placement)`, and FileSkillPlacementStore.save (SkillPlacementStore.swift:35-37) overwrites the whole file. `PlacementCalibration.placement` (PlacementCalibration.swift:63-87) only emits paths that were answered. Both entry points (PathDetailView.swift:63-64 and the SkillPathsView.swift:55-61/74-75 toolbar) build a fresh VM through `environment.makePlacementCalibrationViewModel()`. The bucket math in the scenario holds: pull-up .few → movementRung 4, push-up .several → 3, muscleUp → 3, dip .few → 2. So a dips-only re-answer saves `{dip: 2}`. The VM doc comment ("a downward re-calibration is safe") only covers log-earned rungs. Declared rungs are silently lost.

### A-3 [high] The optional band pull-up rung is treated as a mandatory main-line rung; the "Mam gumę" answer is never used

- **Where:** `cali-park/Features/Skills/Services/ProgressionEngine.swift:64`; also `cali-park/Features/Skills/Services/ProgressionCatalog.swift:60`, `cali-park/Features/Skills/Views/PlacementFormView.swift:105`, `cali-park/Features/Skills/Services/ProgressionFormat.swift:66`, `cali-park/Features/Skills/Services/ProgressionEngine.swift:91`
- **Effort:** M · **Verdict:** confirmed
- **Evidence:** The catalog marks band pull-ups as a side route: `ProgressionStep(exerciseID: ExerciseCatalog.bandPullUpsID, ..., isParallelTrack: true)` (ProgressionCatalog.swift:60). The plan says "guma tworzy tor równoległy, nie obowiązkowy" (mermaid: `band -.tor rownolegly.-> full`), and PROGRESSIONS.md row 4 says "tor równoległy (opcja)". But the engine never reads `isParallelTrack`: `for (index, step) in path.steps.enumerated() where meetsCriterion(...) { logsConqueredThrough = index }` (L53-56) and `let currentRungIndex = min(max(conqueredThrough + 1, 0), rungCount - 1)` (L64). `SkillPlacement.ownedEquipment` / `ownsEquipment` is only read by the calibration VM to pre-fill the toggle (repo grep). Only PathDetailView.swift:170 prints "Tor równoległy — opcjonalny".
- **Impact:** A beginner answers "0" pull-ups, so placement starts them on negatives (rung 2), and later logs 3×5 negatives. The current rung becomes "Podciągnięcia z gumą" even with ownsBand == false. The path card, the Home hint ("następny szczebel" logic) and the progress ring all point at an exercise they cannot do. Their real 3×3 pull-up attempts never show as progress, because progress is scored for the band rung. Two more side effects: logging band pull-ups 3×8 marks negatives (the "fundament") as conquered, and conquering full pull-ups awards +100 XP plus a celebration for a band rung that was never trained. The onboarding toggle "Mam gumę oporową" (PlacementFormView.swift:105) has no effect.
- **Fix:** Make parallel steps optional in the engine. When choosing the current rung, skip a parallel step unless `placement?.ownsEquipment("Resistance bands")`. Do not let a parallel step imply main-line rungs below it, and do not count it as implicitly conquered for XP or celebrations unless it was logged. Make `ProgressionFormat.hintLine` skip parallel steps when naming the next rung. Add engine tests with and without the band.
- **Verifier:** ProgressionEngine.swift:53-64 iterates every step with no check of `isParallelTrack`. A repo-wide grep shows `isParallelTrack` is read only at PathDetailView.swift:170 (label) and in catalog tests. `ownsEquipment` is read only at PlacementCalibrationViewModel.swift:39. A "0" pull-up answer declares rung 2 (PlacementCalibration.swift:28). Logging 3×5 negatives sets conqueredThrough=2, so current = index 3 = band pull-ups (catalog L60), whatever `ownedEquipment` says. `ProgressionFormat.hintLine` (L66-69) names `steps[current+1]` blindly, so a partial-negatives hint says "następny szczebel: Podciągnięcia z gumą". This contradicts PROGRESSIONS.md:28,47,68 and the plan line 94 ("tor równoległy, nie obowiązkowy"). The "implied below" conquest is by design, but applying it to a parallel rung (XP and celebration for an untrained band rung) also follows from the same code.

### A-2 [medium] Lowering the placement floor re-celebrates long-conquered rungs with a false "+100 XP"

- **Where:** `cali-park/Features/Skills/Services/RewardEvaluator.swift:78`; also `cali-park/Features/Skills/Services/RewardEvaluator.swift:47`, `cali-park/Features/Skills/Services/RewardEvaluator.swift:58`
- **Effort:** S · **Verdict:** partially
- **Evidence:** `let floor = placement?.declaredRung(for: path.id) ?? 0` / `for index in 0..<state.conqueredRungCount where index >= floor { references.insert(...) }` (L77-79). Rungs below the floor are left out of `conqueredRungs`, so they are never added to `celebratedRungs` (L58 `celebrated.celebratedRungs.union(conqueredRungs)`). When the floor drops, `let freshRungs = conqueredRungs.subtracting(celebrated.celebratedRungs)` (L47) suddenly contains them. RewardLoopTests has `rungsBelowTheDeclaredFloorDoNotCelebrate` but no test for a floor that later drops.
- **Impact:** Take a user placed at pullUp=4 who logs 3×8 pull-ups. Rung 4 is celebrated and recorded; rungs 0–3 are conquered by logs but never recorded. After any re-calibration that lowers or removes the pull-up declaration (trivial via A-1), the next Skills load queues 4 overlays: "Zwis na drążku +100 XP", "Ściąganie łopatek +100 XP", "Negatywy +100 XP" and "Podciągnięcia z gumą +100 XP". None of these is new, and total XP does not change because XP never depended on placement. This happens for practically every placed user who has trained.
- **Fix:** Separate "seen" from "celebrate". In `evaluate`, add every log-conquered rung (including those below the floor) to `updatedProgress.celebratedRungs`, and emit events only for fresh rungs at or above the floor. Add a test for a floor drop after training.
- **Verifier:** The mechanism is real. In RewardEvaluator.swift, L77-79 skip indices below `floor`, so those rungs never reach `updatedProgress.celebratedRungs` (L58), and the same happens in the baseline at L43. When the floor drops, L47 `freshRungs` contains them. CelebrationPresentation.swift:38 hard-codes "+100 XP" on every rung overlay. Pull-up rungs 0-3 are dead hang, scapular pulls, negatives and band pull-ups (ProgressionCatalog.swift:57-60). No RewardLoopTests case covers a floor drop. I lowered the severity because it only fires after a re-calibration that lowers a floor following training. The result is false overlays with no data or XP change, so "practically every placed user" overstates reach.

### A-4 [medium] Celebrations are marked as celebrated at evaluation time, before they are shown; the evaluation runs at app launch

- **Where:** `cali-park/Features/Skills/ViewModels/SkillPathsViewModel.swift:92`; also `cali-park/Features/Skills/Views/SkillPathsView.swift:17`, `cali-park/Features/Skills/Views/PathDetailView.swift:22`, `cali-park/Features/Main/MainTabView.swift:25`, `cali-park/Features/Skills/Models/RewardEvaluation.swift:8`
- **Effort:** M · **Verdict:** confirmed
- **Evidence:** `try? progressStore.save(evaluation.updatedProgress)` (L92) runs right after evaluation, and the events then live only in memory (`pendingCelebrations.append(...)`, L95-98). The VM's init calls `load()` (L57). SkillPathsView builds the VM inside View.init: `_viewModel = State(initialValue: environment.makeSkillPathsViewModel())` (SkillPathsView.swift:17). That init runs eagerly from MainTabView's `Tab(...) { SkillPathsView(environment: environment) }` (MainTabView.swift:24-26), so the evaluation happens at launch even while the Home tab is shown. The model doc says the opposite: "Persisting `updatedProgress` after presenting `pendingEvents` is what keeps the reward loop idempotent" (RewardEvaluation.swift:8-10).
- **Impact:** A user logs 3×8 from Home or Exercises, closes the app and never opens the Skills tab. On the next launch the VM init finds the fresh rung, saves it as celebrated and queues it in RAM. If the app is killed again before the user opens Skills, that advance (and any level-up) is never celebrated. Every construction of the VM (e.g. any re-init of SkillPathsView or PathDetailView) is a hidden write. A throwaway instance would consume pending events that the kept instance never shows. Because save failures are swallowed by `try?`, a failing write re-queues the same events on every load.
- **Fix:** Keep VM init side-effect free: run `load()` from `.task`/`.onAppear` only. Persist the celebrated record when an event is dismissed (in `dismissCurrentCelebration`), not when it is evaluated. Longer term, evaluate rewards in one shared coordinator on the log-save path, so a save on Home can celebrate where it happens (plan SK6a: "zapis logu/sesji, który domyka kryterium → overlay").
- **Verifier:** SkillPathsViewModel.swift:57 calls `load()` in init. L92 persists `updatedProgress` before the events are shown, and the events live only in the in-memory `pendingCelebrations`/`currentCelebration` (L95-98). RewardEvaluation.swift:8-10 says to persist *after* presenting. SkillPathsView.swift:17 builds the VM in View.init via `State(initialValue:)`. MainTabView.swift:24-26 builds SkillPathsView inside a `Tab {}` content closure, which is non-escaping and so evaluated during MainTabView.body at launch. So the evaluation and save happen at launch, and if the process dies before the Skills tab is opened, those events are lost. The `try?` swallow (L92) is confirmed. The throwaway-instance point is only conditional: AppEnvironment has no @Published, so re-inits of SkillPathsView are rare.

### A-5 [medium] Advancement is scored per log entry, not per session, so supersets and repeated exercises never count

- **Where:** `cali-park/Features/Skills/Services/ProgressionEngine.swift:204`; also `cali-park/Features/Skills/Services/ProgressionEngine.swift:224`, `cali-park/Features/Exercises/ViewModels/QuickWorkoutViewModel.swift:93`, `cali-park/Features/Exercises/ViewModels/QuickWorkoutViewModel.swift:114`
- **Effort:** S · **Verdict:** partially
- **Evidence:** `for entry in logs where entry.exerciseID == exerciseID { let values = qualifyingValues(in: entry, ...); guard values.count >= requiredSets else { continue } ...` (L204-210) scores each WorkoutLogEntry on its own and ignores `sessionID`. QuickWorkoutViewModel.addExercise appends a new item every time: `items.append(DraftItem(exercise: exercise, sets: sets))` (L93). `finish()` saves one entry per item, all with the same `sessionID` (L114-121). WorkoutSession groups those entries as one workout in history.
- **Impact:** The Recommended Routine the criteria come from is trained as supersets (pull-ups / dips alternating). A user who logs pull-ups 8, dips 10, pull-ups 8, dips 10, pull-ups 8 in one Quick Workout has 3 pull-up entries of 1 set each in the same session. History shows one workout, but the engine scores 0 toward 3×8 and the user never advances. The same happens to anyone who saves each set with the SetPad as they go.
- **Fix:** Merge sets per (sessionID ?? entry.id, exerciseID) before scoring, in both bestSessionValue and firstQualifyingDate. Optionally, also merge standalone entries logged on the same calendar day. Add a test with interleaved same-session entries.
- **Verifier:** ProgressionEngine.swift:204-210 and L224-229 score each WorkoutLogEntry on its own and ignore `sessionID`. QuickWorkoutViewModel.addExercise (L91-94) appends a new item even for an exercise already in the session, and `finish()` (L114-121) saves one entry per item with a shared sessionID. A re-added exercise in one Quick Workout is therefore not merged. Overstated: QuickWorkoutView.swift:60-63 lets the user tap an existing item (`editItem`, `initialSets: item.sets`) and append sets to the same entry, so supersets do count when logged that way. Separate standalone SetPad saves (WorkoutLogViewModel.save, nil sessionID) not combining is the documented intent (RungProgress.swift:8-10, test `sameVolumeSplitAcrossSessionsDoesNotAdvance`), not a bug.

### A-11 [low] Engine re-scans the whole log per rung several times per load, and Home recomputes it on every render

- **Where:** `cali-park/Features/Home/ViewModels/HomeDashboardViewModel.swift:119`; also `cali-park/Features/Skills/Services/ProgressionEngine.swift:204`, `cali-park/Features/Skills/ViewModels/SkillPathsViewModel.swift:66`, `cali-park/Features/Skills/Views/PathDetailView.swift:78`
- **Effort:** M · **Verdict:** confirmed
- **Evidence:** `achievementsSummary` and `progressionHint` are computed properties (L119-141). Each render calls `playerLevel` (→ pathStates), `earnedBadges` (→ pathStates), `lastAdvancement` (per-step meetsCriterion) and `mostActionableHint` (→ pathStates). - **Verifier:** HomeDashboardViewModel.swift:119-141: `achievementsSummary` and `progressionHint` are computed properties that call playerLevel, earnedBadges, lastAdvancement and mostActionableHint, each scanning the logs. ## C. Persistence, data integrity, error handling

Persistence is a set of small, synchronous JSON-file stores (log, plans, placement, progress) plus UserDefaults. Writes are atomic and all access stays on the main actor, so there are no cross-thread races. The most serious defect: every load() swallows read and decode errors with try? and returns an empty or nil value. The next append, save or delete then writes that empty state over the real file, so one schema slip or one bad record permanently wipes the training journal or the plans. Other issues: no privacy manifest even though UserDefaults is used (an App Store upload blocker); reviews, photos, comments, likes and event joins are kept only in memory while the UI reports them as saved; versioning is fragile (bare arrays, positional rung indices, case names baked into the JSON keys); recalibration overwrites the whole placement; the reward loop records a celebration as shown the moment it is queued; and all persistence work is whole-file reads and rewrites on the main thread. The Core Data stack has no entities and nothing uses it.

## D. Concurrency, Swift 6 readiness, state ownership

Concurrency hygiene is decent in the newer features. All 11 @Observable view models (Home, Exercises, Planner, Skills, TabRouter) are @MainActor, the stub services are actors, and no @ObservedObject is used for an owned object. The older Parks feature is the Swift 6 blocker: 8 ObservableObject types (3 without @MainActor), a non-Sendable static Park.mock (root cause: public ParkTag), two static var PreferenceKey defaults, an unused Core Data singleton, non-Sendable service protocols that MainActor view models send across isolation, 6 DispatchQueue.main.asyncAfter timers, 9 Task.sleep(nanoseconds:) calls, and a MainActor reentrancy bug in ParkEventsViewModel. App-wide, every view model reads disk synchronously on the main actor in its init, and that init runs from View.init via State(initialValue:); SkillPathsViewModel's init also writes to disk.

MIGRATION PATH. Build settings on the app and cali-parkTests targets (the UI test target only needs SWIFT_VERSION): (0) while still on SWIFT_VERSION=5.0, set SWIFT_STRICT_CONCURRENCY=complete, SWIFT_APPROACHABLE_CONCURRENCY=YES (NonisolatedNonsendingByDefault, InferIsolatedConformances, InferSendableFromCaptures, GlobalActorIsolatedTypesUsability, DisableOutwardActorInference) and SWIFT_DEFAULT_ACTOR_ISOLATION=MainActor. This app is UI-bound and its view models are already MainActor, so MainActor by default fits. Then make these code changes in order:
(1) Make ParkTag non-public or Sendable.
(2) Change the PreferenceKey defaults to static let; delete the unused HeaderOffsetKey; replace onPreferenceChange with onScrollGeometryChange or onGeometryChange.
(3) Delete PersistenceController, the empty xcdatamodeld and the managedObjectContext injection.

## E. SwiftUI quality, project rules, accessibility, UX

The view layer has two clear halves. Home, Exercises, Skills and Planner are modern and mostly follow the project rules: they use the iOS 18 Tab API, value-based navigationDestination only, @Observable, two-argument onChange, payload-driven sheets, and every view has a preview. Parks, plus the Profile, Community and Home placeholder modules, are legacy code backed by mocks. That half holds almost all rule violations: 122 foregroundColor calls, 12 onTapGesture, 15 image-only buttons with no label, 6 DispatchQueue calls, AnyView, GeometryReader, and 6 of the 8 ObservableObjects. ## F. Architecture & code structure

The app is MVVM with a composition root, and that pattern fits the codebase. What's missing is a shared service layer. Every feature view model talks to file stores and static engines directly, so the same operational logic is copied into each workflow: logging a set or session, refreshing after a save, deriving XP and celebrations, the store load-mutate-save cycle, and set/criterion formatting. Several defects come straight from that duplication. The worst is a data-loss path that is copied into 4 file stores. Others: a double XP toast caused by two reward-loop instances, a stale step sheet after training, and a plan editor that drops reminderTime. Production Home also still renders mock identity and a fake Parks/weather module. Parks runs on a second architecture (ObservableObject, @EnvironmentObject, Combine) and shared domain types are scattered across feature folders.

Recommended target structure (MVVM primary, thin Clean-style service layer secondary; no TCA):
- App/ holds cali_parkApp, MainTabView, TabRouter, the routes, and AppDependencies. AppDependencies is a plain final class (not ObservableObject) that owns long-lived services and provides an EnvironmentValues entry.
- Domain/ (shared training kernel): Exercise*, LoggedSet, WorkoutLogEntry, WorkoutSession, WorkoutStreak, WorkoutPlan/Schedule/Weekday/PlannedExercise; ExerciseCatalog and ProgressionCatalog backed by bundled JSON; Formatting/ with PolishPlural, a MeasureFormat shared by SetLogFormat and ProgressionFormat, and the schedule formatter.
- Services/ (shared mechanics):
  - JSONFileStore<Value> that refuses to overwrite a corrupt file.
  - TrainingJournal (@Observable): entries, revision, log, logSession, delete(ids:).
  - ProgressService: one ProgressSnapshot per journal revision, plus a single app-scoped RewardCenter that owns the celebration queue and XP baseline.
  - WorkoutPlanService: save/delete plus reminder rescheduling.
  - Reminders.
- Features/<X>/{Views,ViewModels}: orchestration only. Home reads ProgressSnapshot and never calls ProgressionEngine directly.
- DesignSystem/: typography that does not shadow SwiftUI names, button styles, chips, cards.
- PreviewSupport/ (#if DEBUG): seeded environments, InMemory* doubles, mocks.

Migration order:
1. JSONFileStore (protects user data).
2. TrainingJournal, replacing the per-call-site reload wiring.
3. ProgressService/RewardCenter.
4. WorkoutPlanService, before reminders Sprint 2.
5. Folder moves and dead-code removal.
6. Parks to @Observable with injected services.

## G. Production readiness, tests, tooling, agent setup

CaliPark is not ready for the App Store yet. There is no PrivacyInfo.xcprivacy even though the app reads and writes UserDefaults, and App Store Connect rejects uploads like that. Default screens show placeholder content: every user is greeted as "Michał", the Warsaw weather tile is fake, Parks/Photos/Calendar run on stubs, and "Premium" is advertised with no StoreKit purchase.
